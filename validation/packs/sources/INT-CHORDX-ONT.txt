# ChordX Knowledge Base (编号待定)

> 前置文件：[chordx_core.md](chordx_core.md)（S1-S12，DRT/DEP）· [chordx_security.md](chordx_security.md)（拿到客户文件后按 SEC.6 判断能否送云端 LLM）· [chordx_public_naming.md](chordx_public_naming.md)（48.10：写本协议时项目名/公司名只做举例，不做叙述主语）

> **状态：草稿。** ONT.1–9 仍是大纲骨架；ONT.10（冷启动到监督学习的演进路径）是**待验证的假设**；ONT.11（脱敏与实体对照表）已在**一个真实项目**验证过。 来源是一次两天黑客松前的需求梳理（邮件自动归类，见 ONT.9），**尚未跑通，更未在第二个项目验证**。下面每节只列"要写什么"，具体内容等真实案例跑完、踩过坑之后再填，别现在写死。

## ONT.1 总览与适用范围

- **要写：** 什么时候用（给企业客户做 AI 落地之前，**在写 DRT 之前**，本节产出是 DRT 的输入）；什么时候不用（纯算法/仿真、无业务概念可建模的项目）
- **要写：** "轻量本体"的定义和边界（最小够用 + 用真实样本验证，不追求先建全再开工）
- **要写：** 和现有协议的位置关系：DRT/DEP 回答"决策怎么路由、流程怎么执行"，本协议回答"业务世界里有什么实体/关系/规则，数据从哪来"

## ONT.2 三层框架

| 层 | 核心问题 | 数据从哪来 | 权威方 |
|---|---|---|---|
| Taxonomy 分类体系 | 它属于哪一类？ | 业务人员的日常叫法 | 业务人员 |
| Ontology 本体 | 有哪些实体？关系是什么？ | 主数据、合同、单据 | 合同和主数据 |
| Rules 规则/知识库 | 什么条件下该判断/执行什么？ | 合同条款、公司 SOP、审批权限表、行业标准条款 | **文件原文，不是个人经验** |

- **要写：** 每层的定义、判断标准（怎么区分一个东西该放哪层）、同一封邮件/同一份单据在三层各自长什么样（例子留 ONT.9）
- **要写：** 层与层的依赖：Rules 依赖 Ontology 的实体，Ontology 的事件类型收敛成 Taxonomy 的受控词表

## ONT.3 需要收集什么数据/文件（清单模板）

- **要写：** 清单表格，列：项目 / 谁提供 / 格式 / 属于哪层 / 敏感度（→SEC.6 密级）/ 缺了怎么办
- **要写：** 常见类别（落地时按行业替换）：主数据（实体清单）、合同/协议模板、SOP 与检查清单、审批权限/授权矩阵、供应商/合作方名单、行业标准条款、历史往来样本 + 人工标注
- **要写：** "客户提供不了"时的降级策略（用行业通用规则先顶上，并显式标注来源为'通用假设'）

## ONT.4 思考步骤

- **要写：** Step 1 定业务决策目标（这套本体服务于哪个决策？避免为建模而建模）
- **要写：** Step 2 抽实体（名词）；区分"实体"和"实体在某关系里的角色"（同一公司在不同合同里角色不同）
- **要写：** Step 3 抽关系和事件（谁-对谁-做了什么-引起什么状态变化）；事件与状态更新的区别（新事件 vs 更新旧事件）
- **要写：** Step 4 收敛 Taxonomy：从业务人员的自由说法 → 受控词表，保留"其他"自填口
- **要写：** Step 5 抽 Rules：每条规则必须标 **来源**（哪份文件/哪一条）+ **可信度**；分"可以写死的规则"和"必须回头读原文的规则"
- **要写：** Step 6 最小够用判定（够支撑哪个决策就停，剩下的记进 ONT.10 待办）

## ONT.5 采集工具设计（标注表）

- **要写：** 标注表列分组：输入列（原始材料）/ 标准答案列（人工判断）/ 依据列（用了哪个文件、哪条规则）/ 关联列（更新的是哪一条）
- **要写：** 下拉 + 允许自填；一项多值用分隔符；主项/次项/其他项三组结构
- **要写：** 哪些列能自动识别（机械解析）、哪些可 AI 预填、哪些必须人工——**标准答案不能由被测系统预填**
- **要写：** 给非技术人员的填写说明和示例文件（说明写进表里，不要只在聊天里讲）

## ONT.6 验证

- **要写：** 人工标准答案的来源与一致性（多人标注时怎么对齐）
- **要写：** 难例清单必须包含：关键信息缺失（如没写实体名）、无需处理的负样本、措辞含糊、需要状态更新
- **要写：** 循环论证风险：用 AI 预标注再让人改会引入锚定偏差；至少一部分样本纯人工独立标注
- **要写：** 覆盖检查：每条规则至少有一个样本触发；每个实体类型至少出现一次

## ONT.7 与 DRT / DEP 衔接（未验证，写的时候再对）

- **待验证：** 实体和关系 → DEP 的数据契约（每个节点的输入输出字段）
- **待验证：** Rules → 决策节点的判断依据；"必须读原文的规则"→ 需要检索/引用的节点
- **待验证：** Taxonomy → 分类节点的标签枚举
- **待验证：** RAG / 冷启动路线与节点边界见 ONT.10.4（含对一份赛前 DEP 草稿的两处修正：拆 Generate + Ranking；"更新还是新建任务"独立成 Matching 节点）

## ONT.8 常见坑（占位，随案例补充）

已知待展开，均为需求梳理阶段的预判，**尚未被实践证实**：

- 角色（Charterer）不是独立实体，是公司在某个合同里的角色
- 一封邮件/单据涉及多个事件，只选一个会丢信息，全多选又没主次
- "更新已有任务"比"新建任务"难，需要判断是不是同一件事
- 关键实体不出现在正文里（靠线程、发件人、上下文推断）
- 把规则库偷偷换成"通用预设规则"，会让人误以为系统读了合同
- AI 预标注带来的锚定偏差

## ONT.9 案例（占位，事件结束后填）

- **案例：** 干散货船运营邮件自动归类与任务生成（实体：船 / 航次 / 合同 / 邮件 / 事件 / 任务；规则来源：合同条款、公司 SOP、审批权限表）
- **要填：** 三层在这个案例里各自的样子；标注表最终版；跑出来的准确率、踩过的坑、哪些设计被推翻
- **注意：** 写进本协议时按 48.10 脱敏，案例只做举例

## ONT.10 从冷启动到监督学习的演进路径（草稿，未验证）

> 来源：一次赛前设计讨论，**尚未在任何项目里跑通**；本节全部是待验证的假设。
> **术语澄清：** 这里说的"把公司数据蒸馏成可用系统"，指的是**专家知识显性化 + 数据逐步变成模型**（knowledge elicitation → data flywheel），**不是**模型蒸馏（teacher→student）；后者只是 Phase 4 的一种手段。

**ONT.10.1 起点路由（先问这三个问题）**

| 起点条件 | 首选路线 |
|---|---|
| 没有标签，但有专家 / 历史案例 / SOP | LLM + RAG + Rules 冷启动 |
| 一开始就有大量高质量标签，且任务定义稳定（如固定文档分类） | 直接 supervised；**先用 LLM few-shot 跑一个基线**对比，别默认一定更好 |
| 标签少，且任务有长尾、需要上下文推理 | 保持 LLM + RAG；supervised 只接其中稳定、高频的映射 |

"多少标签算大量"（大概几千条以上？）是经验假设，**以基线对比为准**，不要写死阈值。

**ONT.10.2 四个阶段**

1. **Phase 1 冷启动：** LLM 做抽取 / 分类，RAG 找历史案例和 SOP，Rules 约束动作；知识来源是专家标注表（ONT.5）。
2. **Phase 2 人在回路：** operator Confirm / Edit / Reject；**Phase 1 就要设计日志**：AI 建议、人最终确认的内容、备注、时间、模型版本，缺一项以后就没有可用的标签。
3. **Phase 3 积累标签：** 从修正日志沉淀训练数据；**必须另留一份独立审计集**（见 10.3）。
4. **Phase 4 supervised 接管稳定高频任务：** 如事件类型、状态、优先级；复杂、长尾、要上下文推理的仍留给 LLM + RAG。
   成熟形态是**四者并存**而不是替换：Supervised（学稳定映射）+ RAG（运行时找外部知识：CP 怎么写、SOP 怎么要求、类似案例怎么处理）+ Rules（不可随意发挥的逻辑）+ LLM（非结构化理解和长尾推理）。
   - **可选（有时间才做）：unsupervised 步骤。** 聚类 / 主题发现用来发现分类体系的缺口、去重、挑选值得标注的样本（active learning）。**输出必须专家复核**，不能代替专家给出的 taxonomy（ONT.2 里 taxonomy 的权威方是业务人员）。

**ONT.10.3 对原讨论的保留（写的时候不要直接抄"数据飞轮"）**

- **"每次人工确认 = 新的 ground truth"是高估。**默认点 Confirm 会带来锚定和自动化偏见。需要独立的审计抽样（纯人工独立标注），并监控确认率异常偏高。
- **评测集要在冷启动阶段就留出**，不能拿来当 few-shot 示例，也不能进 RAG 案例库；案例库和评测集要**按邮件链 / 航次切分**，同一条邮件链不能一半在库里、一半在测试里。
- **案例库和标签本身含敏感信息**，先脱敏再入库（SEC.6、48.10）。
- **何时值得 supervised 化：**高频、稳定，且 LLM 的成本、延迟或一致性已经成为问题；不是"标签多了就一定要换"。

**ONT.10.4 RAG 与 DEP 的对应（待验证）**

- RAG 不是一个软件，是一种架构：Knowledge → Index → Retrieve → Augment → LLM。实现三条路：自己写（embedding + 余弦相似度，几十到上百条案例足够）、框架（LlamaIndex / LangChain）、平台（Dify / Flowise）。**按知识规模选**，Embedding 和向量库可以分别换，不必绑同一家。
- 每条专家案例（一封邮件 + 专家判断）天然就是一个检索单元，不需要文档型 RAG 的复杂切块。
- **知识库（案例 CSV、taxonomy、规则）是 D / E 节点的 knowledge resource，不是运行时的节点**；构建知识库是另一条**离线 DEP**（脱敏 → 标注 → 入库），不要和运行时 DEP 混在一起。
- 按 chordx_core §4–5（D 节点只能是 R/A/M/P 之一，E 节点只能是 G/T/X/S/E/D 之一），检查一份赛前 DEP 草稿后得到两处修正：
  1. "基于案例和规则给出并排序建议动作"混了 Generate 和 Ranking，要拆成 **E（Generate 候选动作）+ D（Ranking 排序）**。
  2. "这封邮件是更新已有任务，还是新任务"是 **Matching（邮件事件 ↔ 已有任务）** 的决策，不能藏在 Task State Update（eXecute）里，需要独立的 D（Matching）节点。这也是演示里最有说服力的一环。

## ONT.10b 操作指引与参考数据表：Rules 层的两种落地形式（2026-10-01，草稿，一个项目验证）

在"轻量本体"之后、"监督学习"之前，可以先加两种**业务专家能直接审核、不需要训练**的知识形式（运行规则见 `chordx_agent.md` §19、§23）：

- **操作指引（playbook）= 把"怎么做"写成数据。** 一份指引一个文件：触发条件（`when`）、回答模式、状态（draft/approved）、来源、所需证据、步骤（每步一个原语）。由业务专家审核后才从 draft 变 approved；回答按步骤汇报 done/missing/not_applicable，"done"必须有真正读到的证据。**用户可见名称用业务词（"操作指引"），内部英文名不对客户暴露。**
- **参考数据表 = 把模型记不准的事实固定下来。** 例：港口间距离、费率、常数。由人从权威工具查得，记录值、来源、日期、备注；命中就由代码回答并说明出处，不命中才交给模型并标"一般估算"。它是"专家维护的查询"，不是实时集成，不能写成已对接。

两者都归在 ONT.2 的 Rules 层，是冷启动路线（LLM + RAG + Rules）的具体部件。

## ONT.11 离线知识构建流程：数据脱敏与实体对照表（已在一个真实项目验证）

> 来源：一次给企业客户的真实邮件文档做本地脱敏。它是"历史往来样本"（ONT.3）进入标注和案例库**之前**的预处理，产出的公司 / 域名 / 邮箱表本身就是 Ontology 层实体表（parties / contacts）的雏形。写进本协议时按 48.10，不放真实名称。

**ONT.11.1 流程**

1. **结构探查，不读原文：**只看"遮罩版式"（字母→A/a、数字→9、汉字→字）、段落数、标题、样式，判断文档结构（有没有标题分节、邮件头、独立邮件的边界）。
2. **本地脚本抽取候选实体，终端只输出数量：**原文不进云端、不进日志。
3. **对照表（真名 → 编号）：**同一实体一个编号，含全部别名；带 `scope`（全局 / 只在某份文档）、`status`（auto / review）、`keep original?`、`group` 列；按编号分组排序，方便复核。
4. **人工只复核少数 review 行：**其余 auto 行不用看。
5. **本地替换 → 泄漏扫描：**用对照表模拟替换，再用一份"应该被替换"的名单回搜残留；另外把邮件头显示名、签名里没在表里的人名列出来。
6. **保护用户改动：**见 ONT.11.3。

**ONT.11.2 经验（每一条都踩过）**

1. **识别是查表，发现才是猜。**全文正则猜名字（"MV 后面的词""全大写短语""公司后缀"）几百行几乎全要人工复核；改成"封闭字典（已知的主实体）+ 文档结构（邮件头 From / To / Cc 直接给出 地址 ↔ 显示名 ↔ 公司）+ 关键词锚定（Tel / 账号）"后，待复核降到几十行，再经人工确认降到二十行以内。先问"有没有已知名单"，没有再谈发现。
2. **同一个词在不同文档里含义可能不同。**例如船名里的一个单词，在讲这条船的文档里指船，在另一份文档里是租家的昵称。对照表要有 `scope` 列；判断依据是该词出现在"哪份文档里"的比例，必要时把上下文摘录成本机临时文件供人看，用完删除。
3. **URL 编码文本会绕过普通匹配。**邮件回复链接里的主题、地址把空格写成 `%20`；边界判断要把它当分隔符；超链接的目标地址（mailto 及其主题参数）也要单独处理，否则名字藏在链接里。
4. **软件生成的技术串会被误认成实体。**邮件客户端给内嵌图片生成的编号（形如 `image001.png@<十六进制>.<十六进制>`）会被当成邮箱和域名；签名里的"Tks / B.Rgds"也会被当成邮箱。要单独剔除。
5. **显示名里的角色标签会让过滤规则丢掉真人名。**如"某某 - Operations SG"，因为含 Operations 被当成部门名而漏掉，是当次最大的漏项（几十处）。所以**必须做覆盖检查**，不能只看"表里有什么"，要看"文里还剩什么"。
6. **同一家公司有多个域名、拼写、别名、语言写法。**按域名根 + 英文全称 + 缩写 + 中文名合并到同一个编号；只差一个字母的域名可能是拼写错误也可能是两家，要人确认；能确认的合并，不能确认的保守处理。
7. **哪些不替换要提前定：**港口 / 地名、日期、金额、条款名项目要用，不替换；船名、公司、人名、邮箱、电话、账号、IMO 号替换。
8. **对照表本身含真名：**只放本机，不进仓库，不外发，不上传。
9. **默认不把原文发给云端；**需要看上下文时，由数据所有者明确授权，并限定范围（只看摘录，不看全文）。

**ONT.11.3 不要覆盖人的修改**

对照表成为"准表"之后，**不能再重跑生成脚本**（会覆盖人的决定）。此后所有改动：

- 改之前先备份；用"重建基线 + 逐格 diff"找出人改过哪些格子，只动没被人改过的格子；
- 人开着 Excel 时不写文件（谁最后保存谁说了算）；需要大改时，**新建文件，不动原文件**；
- 每一批改动用内容（原文 + 类型）指行，不要只用行号（排序和删行后行号会变）。
